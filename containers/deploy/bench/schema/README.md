# Benchmark configuration reference

Generated by `bench/schemadoc` from `schema/experiment.json`, `schema/app.json`, `schema/cluster.json` -- do not edit.
Regenerate with `./schemadoc --write`; `test_bench.sh` fails if this
file is stale.

A blank meaning is a key the schema does not describe yet; they are
tracked in `schema/undocumented.txt`.  Cross-field rules a schema
cannot state live in `benchlib/experiment.py` and are what
`bench validate` adds on top of what is below.

## Application contract

What an application must declare so the runner can drive it without knowing which one it is. Installed into the image at /container/app.d/<app>/app.yaml by build_<app>.sh, beside the prepare/launch/extract hooks. An app with no hooks at all is legal: an app.yaml with just app and binary gets you wall time and a placement verdict, which is the ten-minute entry point that makes the contract adoptable.

## Cluster description

What one cluster provides, stated once and split across two files. sites/<site>.yaml holds what every cluster of that site has in common; sites/<site>/<cluster>.yaml holds what makes this cluster itself. Both are checked against THIS schema -- a site file is a partial cluster description -- and bench/sitegen merges them before generating anything, so the flat block a job sources is unchanged by the split. Merge rules: a scalar takes the cluster's value, a list takes the site's entries then the cluster's, a map merges key by key with the cluster winning. The rules that decide whether a MERGED description is complete are in benchlib/sitefile.py, not here, because neither file alone can satisfy them.

| `select` | string |  | matches `/^[a-z_][a-z0-9_]*=[A-Za-z0-9._-]+(:[a-z_][a-z0-9_]*=[A-Za-z0-9._-]+)*$/` | Scheduler resource clauses that ask for THIS node type, appended to the select directive -- on Casper, cpu_type=genoa. Without it a description says what the hardware is but not how to obtain it, which is worse than saying nothing because it looks authoritative: the first Casper run named no processor and landed on a node type the file did not describe. Use only resources that steer node CHOICE. A node's queue-eligibility tag is not one of them: on a system with a routing queue, selecting on it fights the router rather than directing it. |
| `smt` | integer | yes | at least 1 | Hardware threads per physical core. |
| `smt_stride` | integer |  | at least 1 | Under a block SMT layout, the sibling of CPU c is c + stride. Equal to cores on a machine that enumerates all first siblings before any second. |
| `sockets` | integer |  | at least 1 | Populated sockets per node. Used to derive cores per socket, which is the granularity a rank should not straddle. |
| `target_arch` | string |  | matches `/^[a-z0-9][a-z0-9._-]*$/` | The instruction set this hardware actually runs, in the spelling report_cpu_features prints. Checked against the app binary once at job start, which turns a SIGILL on every rank three hours into a queue into one line before the first cell. Deliberately a check and not an input: the image was built in CI long before this file was read, so a site can only refuse to measure an image, never change it. |
